# Stack benchmark: old `main` vs the current tree

2026-10-25. Three measurements, not one: routing, grounded claim extraction,
and the product-search harness, plus one live end-to-end Kriko Agent turn. No
key or credential is reproduced here.

| Side | Source |
|---|---|
| Before | `origin/main` at `6b3e1c64`, detached worktree `.worktrees/legacy-stack` |
| After | the development tree, now branch `feat/measured-stack` |

The point is not to declare a winner from a small sample. It is to show which
regressions are gone, what the current stack actually costs, and where
"better" is still unmeasured.

## 1. Routing: 42 messages

`chat.route_message` from each tree. No model, no network, no spend. Expected
labels are the intent of the message, written before the run.

|  | Old | New |
|---|---:|---:|
| Correct route | **33 / 42** | **42 / 42** |

The nine old misses and their new routes:

| Message | Expected | Old | New |
|---|---|---|---|
| What goes wrong with the 2020 Golf? | catalogue | chat | catalogue |
| What usually fails on a Bosch GBH 2-26? | catalogue | chat | catalogue |
| Common problems with the Dell XPS 13 | catalogue | web | catalogue |
| Is the 2021 model known to fail? | catalogue | chat | catalogue |
| Failure modes of the DQ200 gearbox | catalogue | web | catalogue |
| What wears out on the Trek Marlin 7? | catalogue | chat | catalogue |
| What breaks on the Dyson V11? | catalogue | chat | catalogue |
| 2020 Golf'ta ne bozulur? | catalogue | chat | catalogue |
| Bosch GBH 2-26'da sık görülen arızalar? | catalogue | chat | catalogue |

The benchmark itself caught two regressions that were then fixed:

- `Search the web for what goes wrong with the 2020 Golf.` was routed to the
  catalogue because the failure phrase was checked before the explicit request
  for the web. `_EXPLICIT_WEB` now wins first.
- The Turkish `sık görülen arızalar` (plural suffix) was not matched until the
  Turkish stem allowed a suffix.

All 26 ordinary-chat, buying and explicit-web messages stayed where they
belonged. The seven English failure questions that used to go to chat now read
records; the two Turkish ones do too.

## 2. Claim extractor: eight documents, old vs new

Same key, same model (`deepseek-v4-flash`), same input text. Old = the
`doc.text[:6000]` extractor; new = overlapping chunks with the widened signal
gate.

| Case | Expected claims | Old | New | Old grounded | New grounded | Old calls | New calls | Old s | New s |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| tail claim at 8.3k | 1 | 0 | 1 | 0 | 1 | 1 | 3 | 5.90 | 11.03 |
| middle claim at 6.5k | 1 | 0 | 1 | 0 | 1 | 1 | 3 | 1.07 | 6.21 |
| short English, 3 claims | 3 | 3 | 3 | 3 | 3 | 1 | 1 | 11.64 | 8.79 |
| Turkish, 2 claims | 2 | 2 | 2 | 2 | 2 | 1 | 1 | 7.76 | 5.41 |
| generic advice | 0 | 0 | 0 | 0 | 0 | 1 | 1 | 1.76 | 1.28 |
| routine servicing | 0 | 0 | 0 | 0 | 0 | 1 | 1 | 1.06 | 1.42 |
| two claims in one long doc | 2 | 1 | 2 | 1 | 2 | 1 | 3 | 5.17 | 7.34 |
| crack/seepage in the middle | 1 | 1 | 1 | 1 | 1 | 1 | 3 | 4.06 | 5.45 |

Old: **5 / 8** cases had the expected claims; new: **8 / 8**. The new path
spends more calls and wall time on long documents — roughly 3 calls and 5–11
seconds instead of 1 call and 1–6 seconds. That is the cost of reading past
6,000 characters, and `MAX_CHUNKS` bounds it.

The long-document claims are verbatim and grounded in both cases where they
are found; the old failures are omissions, not wrong claims.

## 3. Product-search harness: 20 live runs

`app.searchbench` on five cases × two models × two strategies, one repetition.
All 20 runs succeeded. **Quality is not scored here** — the harness records
answer-term coverage and citations, not factual correctness.

| Model | Strategy | OK | Median latency | Mean tokens/run | Mean $/attempt | Pages read/run | Searches |
|---|---|---:|---:|---:|---:|---:|---:|
| Mercury 2.5 | eager | 5/5 | 6.77 s | 27,485 | $0.006139 | 8.2 | 11 |
| Mercury 3 | eager | 5/5 | 8.71 s | 72,628 | $0.007598 | 14.6 | 23 |
| Mercury 2.5 | parallel | 5/5 | 6.04 s | 35,425 | $0.010278 | 9.8 | 15 |
| Mercury 3 | parallel | 5/5 | 6.36 s | 57,130 | $0.007381 | 12.8 | 19 |

Two honest readings:

- Mercury 3 is **not automatically cheaper per answer**. In the eager profile
  it chose more than twice the searches (23 vs 11), read more pages, and cost
  more per attempt. The paired latency difference against Mercury 3 parallel
  was +0.06 s (95% CI −3.13 to 2.64) for eager and +1.35 s (−4.58 to 7.06) for
  Mercury 2.5 parallel; none is a settled difference.
- Where the work is comparable, the token price is roughly half. In the live
  Kriko Agent turn in the next section, identical tokens cost 44% less on
  Mercury 3 once the fixed DeepSeek call cost is included.

The harness runs Mercury 3 at `instant` and Mercury 2.5 at `low`, while Kriko
Agent uses `low` for both, so this table is a model-behaviour comparison, not
the app's exact configuration.

## 4. One live Kriko Agent turn

Mercury 3 + DeepSeek Search/Fetch + the app-action executor, fresh app state.

Question: “What goes wrong with a 2016 Volkswagen Golf 1.6 TDI? Search the web
for owner reports and cite the pages. Also remember that I care about timing
chain failures.”

| Measurement | Value |
|---|---|
| Error | none |
| Latency | 11.45 s |
| Tokens | 31,610 in / 3,901 out |
| Retrieval | 4 queries, 2 billable calls, 2 cache hits, 8 pages |
| Action | `remember` → “Cares about timing chain failures on the 2016 VW Golf 1.6 TDI” |
| Profile after the turn | the row is in **Must have** |
| Cost, current | **$0.006026** |
| Same tokens at Mercury 2.5 prices | $0.010748 |

The answer corrected the premise: the 2016 EA288 1.6 TDI uses a timing **belt**,
not a valve-train chain, with the 210,000 km interval quoted from Auto Motor und
Sport and CompleteCar.ie. It then named injector failures (including the
03L130277B series), the high-pressure fuel pump, EGR cooler/valve clogging and
DPF clogging, each with a page and a quotation.

## What this establishes

- The product-failure route is no longer generic chat: 42/42 vs 33/42 on the
  routing matrix, including two Turkish phrasings.
- Whole-document extraction recovers claims the 6,000-character cap lost: 8/8
  vs 5/8 on the extractor matrix.
- Mercury 3, DeepSeek retrieval and the app-action vocabulary work together in
  one live turn, with the action persisted.
- On identical tokens, Mercury 3 is about 44% cheaper.

## What it does not establish

- A quality distribution. The search harness scores structure, not correctness;
  the routing labels and extractor cases are small, hand-written sets.
- That Mercury 3 is always cheaper. Its extra retrieval can erase the rate
  advantage, as the eager profile shows.
- Packaged-app behaviour: the action cards were not observed in a built desktop
  or mobile package.
- General language coverage: two Turkish failure questions are covered because
  they were in the matrix, not because Turkish is solved.
- That long-document extraction is affordable: the pack builder has
  `MAX_CHUNKS`, not a token budget.

## Reproduce

```text
# routing: start from each tree, no keys
python -c "from app import chat; print(chat.route_message('What goes wrong with the 2020 Golf?'))"

# extractor: the same text through each tree
python tools/try_claim_extractor.py --file long-thread.txt

# product-search harness
python -m app.searchbench run --models mercury-3,mercury-2.5 --searches deepseek-content \
  --reps 1 --limit 5 --timeout 60 --max-tokens 4096 --results 4 --page-chars 6000 --http2

# live stack turn
# the turn behind the table was run through kriko_agent.converse with a fresh
# app.sqlite and the app-action executor; see .dsh-tmp/prove_turn.py for that
# one-off runner
```
