## Finding

“Gemma4a2b” is not a Google-published Gemma 4 model name. Google’s current Gemma 4 model card lists E2B, E4B, 12B, 26B A4B, and 31B; the repository already recommends the distinct Ollama tag `gemma4:e2b`. Treat any other spelling as an unresolved third-party tag until its publisher and weights are identified. “E2B” means effective 2-billion parameters (5.1B including PLE); “A4B” is the active-parameter label for the 26B mixture-of-experts model. The similarly spelled “A2B” cannot be silently substituted for either.

The controlled in-repository comparison from 2026-10-11 tested **Gemma 3n E2B**, not Gemma 4 E2B. On that older pipeline snapshot it recovered 0/2 expected problems, while Qwen 3.5 4B recovered 2/2; later pipeline changes mean that record is historical evidence only. A separate tracked artifact, [`2026-10-12-small-model-cpu-release.jsonl`](2026-10-12-small-model-cpu-release.jsonl), records two `gemma4:e2b` cases at pipeline digest `e686996dd0dadaa54e653ae0065e089521c9c4425284f3394d265f08c9e57e98`: the evidence case recorded both expected findings, zero unexpected findings, 4,894 tokens and 210.51 seconds; the abstention case abstained with zero unexpected findings, 1,350 tokens and 45.821 seconds. The rows do not include host or runtime metadata, so their CPU/runtime label cannot be independently checked from the artifact. The earlier [live search follow-up](2026-10-11-local-search-followup.md) also records one `gemma4:e2b` retrieval run: 73.26 seconds, six extraction passes, and zero retained findings. That is a single task observation, not a model-reliability benchmark. The current 1.6.0 evaluator digest is `e647d1c957e01a8972ddef64ed0834a17ceb622613e0e1d998c8aa2affec6055`; there is no same-pipeline Gemma 4 result. These records do not establish that Gemma 4 E2B is better or worse than another model. Do not change the recommendation on that basis.

## Recommendation and evidence limits

Keep the existing Ollama runtime and `gemma4:e2b` recommendation while measuring it. Compare candidates only on identical prompts, sources, pipeline revision, context, output budgets, and quantization where possible. Use the existing evaluator’s fictional evidence and abstention cases; report the pipeline digest, runtime, exact model tag, context, temperature, calls/tokens, latency, supported-finding recall, unsupported claims, wrong-model leakage, abstention, and source diversity. The evaluator records host OS/architecture/CPU count and Ollama’s reported loaded-model memory, VRAM and context where available; these do not estimate peak RAM, power use, or quality on a different device. Fixture results are a regression signal, not a substitute for a held-out real product set or a local hardware run.

Preserve the pipeline’s current separation of responsibilities: model-proposed evidence IDs and JSON are untrusted, Python copies exact source text, deterministic identity/number/reference checks reject unsupported claims, and model verification is an additional filter rather than proof. If a runtime refuses structured output, diagnose that degradation instead of quietly removing the constraint when only another optional request field was refused.

Do not fine-tune yet. First establish whether misses come from retrieval, the evidence window, schema compliance, extraction, applicability checking, or rendering. Fine-tuning becomes a justified experiment only after collecting reviewed, permissioned, held-out examples and a reproducible base-model baseline. If a fixed tool API becomes the bottleneck, FunctionGemma is a separate candidate for that closed action set; it is not a generic Quick Look model.

## Repository baseline observed

- `src/app/localplane.py` currently recommends `gemma4:e2b`; `src/app/localruntime.py` and `src/app/providers/local_inference.py` already target local Ollama/OpenAI-compatible serving.
- `src/app/providers/local_pipeline.py` performs source-scoped extraction, exact quote copying, identity/conflict/numeric checks, source-kind checks, verification, and rejection/coverage reporting. These guards are stronger factual controls than asking a larger model to self-certify.
- It also excludes spans with explicit instruction-injection markers before extraction. A scripted test verifies that an ordinary supported failure remains quotable while a prompt-injected motor claim is omitted from the model's evidence window.
- `docs/benchmarks/2026-10-11-local-pipeline.md` reports a controlled **Gemma 3n E2B** result on an older pipeline snapshot. It is not a Gemma 4 result.
- The current sandbox is not a target Mac/Apple-Silicon machine and had no Gemma 4 weights available for a new run. The tracked prior Gemma 4 artifact above is historical and lacks runtime/host metadata. Tests can prove request negotiation and deterministic pipeline behavior; they cannot establish current-pipeline model quality or target-device latency.

## Implementation evidence and limits

The 400-regression test was first run against the old socket and failed because the retry omitted the response_format field after a response that named only reasoning_effort. With the fix, the retry removes the unsupported effort field while retaining json_schema. Scripted tests also cover the json_object compatibility mode, reuse of the negotiated mode, reporting when both schema formats are refused, and preserving reasoning effort when an ambiguous error was actually caused by schema support. A pipeline fixture test keeps the exact supported failure quote and confirms an injected motor claim never enters the model's evidence prompt. These are deterministic protocol/pipeline tests; no live model generation was available, so they say nothing about Gemma quality, end-to-end latency, or Apple-Silicon performance.

When a real evaluator run is available, tools/evaluate_local_pipeline.py emits exact model/context/settings, pipeline digest, model calls/tokens, latency, result/coverage (including structured-output mode), host metadata, and Ollama's loaded-model/device report where available. An OpenAI-compatible server that cannot report its device remains unknown.

### Why no current-pipeline Gemma 4 benchmark was run here

The tracked earlier Gemma 4 artifact is not a 1.6.0 benchmark: its pipeline digest (`e686996d…`) differs from the current evaluator digest (`e647d1c9…`), and its rows omit runtime and host metadata. On 2026-10-12 the available Linux x86_64 worker reported 9.7 GiB total RAM, 5.8 GiB available, and no swap; `/workspace` had 24 GiB free and `/tmp` 2.6 GiB free. No Ollama executable was installed. The [Ollama `gemma4:e2b` listing](https://ollama.com/library/gemma4) was 4.6 GB, and its [registry manifest](https://registry.ollama.ai/v2/library/gemma4/manifests/e2b) listed 3,502,493,472 bytes of model weights, 986,833,664 bytes of projector, and 97,817,696 bytes of draft weights (about 4.59 GB decimal total, before runtime and inference cache). That leaves little RAM headroom on this worker for context/KV cache and the server, with no swap safety margin. The checked [Ollama Linux amd64 release archive (`v0.40.3`)](https://github.com/ollama/ollama/releases/tag/v0.40.3) was 1,437,349,190 bytes; that is a compressed download size, not resident-memory use. Workspace disk was sufficient for the weights, but staging and loading them during concurrent native builds risked resource pressure without improving the current-pipeline comparison, so no runtime or model was downloaded for a new run. No 1.6.0 model-quality or latency score is claimed. These are this worker's measurements and metadata, not minimum requirements for a user's Mac.
