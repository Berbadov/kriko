# Kriko 0.3.14 verification

Cut from `main` at the merge of #344 (gaming monitors and condensing combi
boilers), #345 (the agent harness plane rebuilt) and #346 (source credibility
tiers), on top of the 0.3.13 release commit. The extension keeps its 0.5.0
manifest; the website and the phone app live in their own repositories.

## What changed

- Two catalogs: `packs/gaming-monitors` (17 models, 50 claims) and
  `packs/condensing-combi-boilers` (12 series, 38 claims), both with their own
  `pack.toml`, vocabulary, research templates and coverage. The release now
  builds 34 `.kpack` files instead of 32.
- Source credibility: `kriko/pack/credibility.py` sorts every source URL into
  `official`, `press`, `community`, `commercial`, `weak` or `unknown`, writes
  `sources.source_tier` per row and `packs.credibility_json` per pack, and
  applies three rules (a `high` claim needs an official source; a claim of only
  weak or unknown sources has nothing to check; a community-only claim needs
  two distinct domains). Recorded by default; `kriko build
  --strict-credibility` fails the build instead. A pack's own
  `trust/source_tiers.yaml` fills in domains the shared lists do not know.
  Documented in `docs/PACK_CONTRACT.md`.
- Harness plane: `opencode` and `hermes` join `claude` and `vibe` as resident
  ACP workers, each with a per-run policy and its own config written per run;
  every roster row is reachable again. Per-call deadlines are checked against
  the phase floor rather than zero. A CLI's own cheap account check is
  preflighted and its verdict cached for ten minutes (`signed_out`,
  `exhausted`); account walls reported by a run are cached the same way, and
  Claude Code's "5-hour limit" sentence now matches. A model id not on this
  machine's list is refused at run start. Slow CLIs (`hermes`, `agy`) get a
  30-second probe budget inside a 45-second ceiling.
- Page reads: `_page_budget` never exceeds the reader's document budget, and
  the answer, revision and review phases reuse pages already fetched in the
  same job.
- Time: `_Turn.cut_short` returns the pages already read with
  `status: "out_of_time"` instead of discarding them with the exception.
- Windows: a run's temporary folder is torn down through `run_directory`,
  whose failure is logged rather than raised over the run's own error, and
  `reap_stale_run_dirs` sweeps `kriko-agent-*` and `kriko-research-*` folders
  older than a day at startup.
- `kriko/pack/credibility.py`'s `judge` had an unannotated `texts` local and
  `cli.py::cmd_build` an unannotated `reports` list that mypy 2.4.1 rejected on
  `main` (one `call-overload` and one `var-annotated` error); both are
  annotated in this release so the gate's mypy stage is green.

## What was and was not observed

See `0.3.14.json`. On the final tree, every stage of `tools/gate.sh` ran on the
Windows host that builds the installer. Ruff and all four mypy runs are clean
(`src/kriko` 41 files, `src/app` 271, `packs` 53, `server` 8). The Python suite
ends at 5318 passed, 29 skipped and 18 failed, none of them from this release:
16 fail identically on a clean `origin/main` (the network-dependent agent bench
and failure-class tests, the codex help-probe test, and the directory-order
invariant that #345's `base.glob(pattern)` trips), and 2 are load flakes that
pass when run alone. `wheel`, `node` (539 tests), `ui` (build, oxlint with
warnings only, 123 tests) and `tauri` (`cargo check`, 13 shell tests, 2 harness
tests) are green.

Two unannotated locals in the new credibility code (`credibility.judge`'s
`texts`, `cli.cmd_build`'s `reports`) were not accepted by the mypy 2.4.1 this
host runs; both are annotated here, which is the only source change this
release makes beyond the version bump.

The Windows installer, portable ZIP and engine ZIP were built with
`kriko-ui/package.ps1 -Version 0.3.14` from this worktree, and the build's own
checks passed: the shared-access pepper was configured, the frozen engine
answered its handshake and served `/api/health` at version 0.3.14, an MCP
`initialize` was answered, a job failed cleanly, and the app stayed up for 25
seconds with its engine spawned. The installer's first `makensis` invocation
failed while a full pytest run was saturating the machine; the same bundle
recipe then succeeded, and a complete rerun of the recipe then ran to
completion. The
installer was not installed and no reader journey was walked on a packaged
window, so `tools/release_readiness.py` still refuses complete stable
certification, as it did for 0.3.10-0.3.13. No macOS disk image was built. The
34 catalogs, `packs.json`, `packs-0.3.14.zip` and the unchanged extension ZIP
(manifest 0.5.0) are attached beside the installer, and `SHA256SUMS-ALL.txt`
covers every attached file.
