# Kriko 0.4.0 verification

Cut from `release/0.4.0` at the merge of #355 (the desktop app redrawn after the
phone app, procurement on every screen, and one plain Settings screen). The
browser extension is 0.5.1; the website and the phone app live in their own
repositories.

## What changed

- **The desktop app is the phone app's system.** `kriko-ui/src/styles/tokens.css`
  defines four palettes (dark, gray, paper, white) and `system`, and every role
  reads them; a stored `light` reads as paper. `src/styles/system.css` is the
  shared list, row and figure vocabulary the screens are drawn from. A labelled
  rail (`src/ui/Rail.tsx`: Check, Procure, Library, Settings) replaces
  `ui/Drawer.tsx` and `ui/TopBar.tsx`; `showDrawer()` still names a place and
  routes through `routeFor`, so the tour, the agent's Open buttons and the
  engine's notices reach the same places.
- **Settings is one screen** (`src/screens/Settings.tsx`) with six sections:
  General, Research, Keys and models, Connections, Usage and spend, Data and
  updates. The Agents, Chat, Local model, Setup, Search, Proxies, Chat clients,
  Backups, Logs and Report panels are mounted inside them. The search field
  reads each row's `[data-setting]` label and note from a hidden copy of every
  section.
- **Procurement is one module** (`src/engine/procurement.ts`: `summarize`,
  `linesOf`, `findProduct`, `addToEstimate`) read by Procurement, Ask, Product
  and Compare. The Procurement desk replaces the old Estimate screen with
  per-currency committed gross, quotes expiring within 14 days, expired quotes,
  lines at risk, unpriced lines, uncomparable currencies and a landed-cost
  comparison per line. `src/screens/procurement/` holds the desk's parts.
- **Defects fixed in the same branch.** A quote in the estimate's own currency
  converts at 1 instead of being dropped; the accounting sheet converts net, VAT
  and gross or leaves the cell blank; Add a product calls `/api/search` (the
  engine shadows `/api/subjects/search` with a 404); the duplicate Automatic
  language option is gone; the gray palette defines the four raw colours it
  missed; a stray CSS declaration that stopped the production minifier is
  removed; saved chats are a Chats list on History again.
- **Extension 0.5.1** repaints `hover_lite/hover_lite.css`, `options/options.css`,
  the in-page checkout card and price toast (`hover_lite/hover_lite.js`), the
  injected notice (`background.js`) and the learned-page mark (`content.js`) in
  the app's dark and paper values. No route the extension calls changed: every
  call site still names a route the engine serves
  (`src/app/tests/test_the_clients_call_routes_that_exist.py`).
- **Tooling.** JavaScript packages install and build with Bun 1.4.5
  (`packageManager` in both `package.json` files, `bun.lock` committed, both
  `package-lock.json` files removed); the suites still run under `node --test`.
  `tools/gate.sh` runs py, node, ui and tauri at once and then the wheel alone
  (`GATE_CONCURRENT=0` is the serial path), because the wheel stage deletes and
  rebuilds `src/*.egg-info` and `build/lib` and starved the tests when it ran
  beside them. `desktop.yml` caches Bun, pip and cargo on the lockfiles.
- **Two test guards made honest, not weaker.** The PowerShell parser check
  tries each PowerShell the machine has and skips only when none can start,
  after a Windows App Execution Alias stub made `CreateProcess` fail with
  WinError 5 and took the whole gate down. The linear-time page test measures a
  batch of eight small reads against one large read in the same round and takes
  the best round, because Windows' `process_time` ticks at 15.6 ms and a busy
  machine reported a ratio of ten for a linear parser; a quadratic parser still
  reports sixteen in every round.

## What was and was not observed

See `0.4.0.json`. The walks below were done in the packaged 0.4.0 portable
window on this Windows host (WebView2, driven through its own DevTools
protocol), against a scratch `KRIKO_STORE`/`KRIKO_APP_STATE`, with the
`laptops` catalog installed from the v0.3.14 release.

- **Portable start**: the archive was extracted, `kriko.exe` opened, its own
  `kriko-sidecar.exe` started beside it (`shell_attached: true`), `/api/health`
  answered at 0.4.0, and the redesigned Ask screen rendered (rail, question,
  ideas).
- **Setup**: Settings opened with the six sections; Research showed
  **Claude Code** as the answering agent, **Ready**. `POST /api/agent-verify`
  started the MCP server from the packaged sidecar and answered
  `ok: true, server: "kriko"` with all 22 tools.
- **Sourced answer**: "What is known to go wrong with the MacBook Air M2?"
  answered by Claude Code (`claude-haiku-5-5`, Claude Code 2.1.323) after six
  searches and six pages read; the Product dossier showed 4 risks, 3 serious,
  each with its source and its "Partial: only one site says this" note.
- **Follow-up**: "Which of those is the most serious for a used 2022 model?"
  was answered in the same conversation with three new cited pages.
- **Compare**: the ThinkPad T14 check (3 risks) and the MacBook Air M2 check
  (4 risks) were both added and drawn side by side, with per-product research
  coverage and the "In 1 of 2 products" finding rows.
- **Stop**: a Compare question was stopped 8.1 s into its turn; the turn reads
  **Stopped** and kept its log. No answer text had been written yet, so there
  was no partial text to preserve.
- **Upgrade retains data**: a scratch profile was started on the 0.3.14
  portable build, the `laptops` catalog was installed (9 subjects, 38 claims)
  and a chat thread was created; the 0.4.0 portable build then opened on the
  same profile with the catalog and the chat thread present.
- **Reconnect: did not recover.** Killing the packaged `kriko-sidecar`
  produced the failure screen with the engine's last lines, as designed. Two
  presses of **Reconnect** left the window offline ("Could not reach Kriko")
  while the shell's own `engine_status` said `ready` at 0.4.0 and a new
  sidecar answered on 8787. That is a defect in the retry path, not in this
  release's changes; it is recorded here rather than reported as passed.
- **Fresh install: not walked.** A Kriko 0.3.14 is installed on this machine
  (`%LOCALAPPDATA%\Kriko`, per-user uninstall entry), and
  `packaging/smoke_installer.py` refuses to replace a reader's install with a
  scratch copy. The installer was built and the app it carries was started;
  the installer itself was not run here.

**Providers observed**: Claude Code 2.1.323, model `claude-haiku-5-5`, two
turns, $0.0075 and $0.0083 on the reader's own subscription, both answering
from searched and read pages with cited sources.

## The build

`tools/gate.sh` on this tree, on the Windows host that builds the installer:
**all gates passed**. The py stage (version agreement, ruff, four mypy runs,
pytest) ended at 5354 passed, 29 skipped, 0 failed in 14m38; the concurrent run
of the other stages passed node (550 tests) in 10s, ui (build, lint, 256
behaviour tests) in 31s, tauri (cargo check and test, the shell and the
harness) in 53s, and wheel in 54s. Wall time for the concurrent run was
27m56s; the sum of its stage times is 16m54s of real work plus pytest, so
running the independent stages at once is what keeps the gate near the Python
suite's own cost.

The Windows installer, portable ZIP and engine ZIP were built with
`kriko-ui/package.ps1 -Version 0.4.0` from this worktree (without
`-InstallCheck`, for the reason above). The build's own checks ran: the pepper
was reused, the frozen engine answered its handshake and `/api/health` at
0.4.0, the Firefox staging answered with the offline event-page manifest, the
MCP server answered `initialize`, a job failed cleanly, the app opened and
stayed up for 25 s with its engine spawned, and the portable ZIP was written.
The first freeze's `smoke_sidecar.py` failed at its Firefox assertion, because
`#354` had changed the event page to load the offline reader first and the
check still expected one script; the check is updated to the new intent. It
also failed once to finish a job within 30 s while 157 stale `kriko-agent-*`
folders in `%TEMP%` were being reaped at startup; after they were removed every
check passed.

Sizes and digests are in the release notes and `SHA256SUMS.txt`.
