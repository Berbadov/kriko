# Kriko 0.3.1 — verification record

What was observed before this release was published, what was not, and who
decided to publish anyway. Written the same day the build was made
(2026-10-23), on the machine it ships from.

## What the release contains

| Asset | What it is |
|---|---|
| `kriko-0.3.1-x86_64-setup.exe` | Windows x64 installer, per user, unsigned |
| `kriko-0.3.1-win64-portable.zip` | The two programs and OpenSERP, no install |
| `kriko-engine-0.3.1-win64.zip` | The engine alone, for the in-app engine updater |
| `engine.json` | The updater's manifest (`min_shell` 0.3.1) |
| `SHA256SUMS.txt` | The three Windows downloads, as the in-app updater reads it |
| `SHA256SUMS-ALL.txt` | Every asset in this release except itself |

No catalogs are published with this release. The two that travelled with earlier
releases (`cars.kpack`, `drill.kpack`) are example data, and the maintainer asked
for them to be left out. `packs.json` is therefore absent as well: the app looks
for it at `releases/latest/download/packs.json`, and with this release that
address has no file.

## Observed, on this machine

| What | How |
|---|---|
| The gate | `tools/gate.sh`: version agreement, ruff, mypy (three runs), pytest **4,445 passed / 22 skipped**, the wheel, both JS suites (460 extension, 33 desktop), the website, and `cargo check` + `cargo test` for the shell. Every stage green. |
| The build | `kriko-ui/package.ps1`: the sidecar froze and answered its handshake, the web interface built, the app and installer built, and the app's own start-up check ran — "the app stayed up for 25s and did not panic; engine spawned: yes". |
| The shipped engine | The portable zip was extracted and its `kriko-sidecar.exe` run against an isolated store: `/api/health` reported **0.3.1**, every agent row carried the new search dial with `own` as its default and both choices, and `/api/keys/shared/status` reported `bound: true`, `device: dpapi`. |
| Shared access, end to end | A code sealed by this tree's pepper opened in the shipped sidecar (200; `grant.present: true`, state `shared`), a code sealed with a different pepper was refused (422), and the file the sidecar kept (`shared.json`) contained no key in the clear. |
| The changed screens | Against a source engine on an isolated store, through Chrome's DevTools protocol: the top-bar **Settings** gear opens Settings directly; the drawer's list has 11 rows and reopens on the list after a panel is closed; the **Shared access** group renders with its password/code fields and the trial line; the **Agents** panel shows the **Web search** dial on every agent row with its two choices; `PUT /api/prefs` stores `kriko`, and a value outside the vocabulary gets a 422 naming the allowed set. |

## Not observed

These are the release gate's own journeys (`tools/release_readiness.py`). None of
them was walked on the packaged build, so the gate refuses, and
`docs/releases/0.3.1.json` records each one as not observed rather than
pretending otherwise.

`fresh_install`, `portable_start` (the app itself; its engine was started),
`setup`, `sourced_answer`, `follow_up`, `compare`, `stop`, `reconnect`,
`upgrade_retains_data`.

No provider was called. This machine had no Mercury, DeepSeek, Exa, Tavily or
OpenAI key available to the engine during the work, so **no Kriko Agent turn, no
paid answer and no hosted search was run live**. Everything about those paths is
pinned by tests that stub the network edge, not by an observation.

## Known limits of this release

- The Windows installer is **unsigned**. SmartScreen warns on first run.
- The Kriko Agent is still marked **Soon** and is still experimental.
- A shared access code binds to the **build** that made it: rebuilding elsewhere
  without `src/app/sharekeys_pepper.py` produces a build whose codes do not open
  each other. Rotating that file stops every code already handed out.
- The free trial is **not** in this build: no trial bundle was baked, because
  baking one needs a key pair the owner must make and cap at the provider first
  (`tools/make_trial_access.py`).
- A friend given an access code can recover the keys on their own machine, and
  the app's local HTTP API remains unauthenticated. `docs/security/shared-access.md`
  says so in full.

## Who decided

The maintainer asked for the release ("you can release it thanks") after the
report above was given, with the unobserved journeys and the live-provider gap
stated. The same posture as 0.3.0: the gate that cannot be observed is recorded,
not waived silently.
